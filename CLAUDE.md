# Инструкции для работы над проектом

Этот файл читается автоматически в начале каждой сессии. Здесь то, что нельзя вывести из кода.

Отвечай пользователю на русском языке.

Если по ходу работы что-то здесь устарело — сменился стек, команда, архитектурное решение, — обнови этот файл тем же изменением, а не оставляй расхождение на потом.

## Что это за проект

Конструктор печатных карточек с переменными данными. Подробности — в `README.md`, схема документа — в `docs/document-model.md`, план — в `docs/roadmap.md`, раскладка экранов — в `docs/ui-spec.md`.

Работаем по этапам из роадмапа последовательно. Не начинай следующий, пока текущий не закончен и не проверен вручную в браузере.

## Команды

- `npm install` — установка зависимостей
- `npm run dev` — dev-сервер (Vite)
- `npm run build` — проверка типов (`tsc -b`) и продакшен-сборка
- `npm run lint` — Biome, линт и проверка форматирования
- `npm run format` — Biome, форматирование с записью
- `npm run preview` — локальный просмотр собранного `dist/`
- `npm test` — Vitest (`vitest run`), среда node без jsdom

Линтер и форматтер — только Biome (`biome.json`), ESLint/Prettier не добавляем. `reference/` из проверки Biome исключён: это замороженный прототип, его не переписываем.

## Дизайн-система и мокапы

Дизайн-система живёт в Claude Design, проект **Cutline Design System** (`projectId` `7ee489d8-7b16-4f32-adec-fbaac1f7571b`) — токены (цвета, типографика, spacing), React-компоненты (`Button`, `TextField`, `LayerRow` и т.д.) и полный набор мокапов редактора: режимы **Дизайн** и **Данные**, обязательные состояния (ничего не выделено / выделен элемент / переполнение текста), диалог экспорта, импорт CSV.

**`/design-sync` тут не подходит** — этот скилл синхронизирует в обратную сторону: локальную библиотеку компонентов *в* Claude Design, а не мокапы *из* него. У нас наоборот: дизайн-система уже готова в Claude Design, а в репозитории своей нет. Токены и переиспользуемые компоненты (`components/core`, `forms`, `feedback`, `overlays`, `editor` — не `ui_kits/`) читаются вручную через `DesignSync`(`get_file`/`list_files`, read-only, без запроса прав) и переносятся в `src/ui/` как строгий TypeScript — .jsx→.tsx, `.d.ts` сливается в тот же файл интерфейсом `<Name>Props` (отдельных `.d.ts` в проекте нет, см. `src/model/document.ts`).

`ui_kits/editor/*` (Chrome/Canvas/Inspector/DataView/DataImport) — не переносить как код: это собранные макеты экранов на фейковых данных, а не переиспользуемые части. Смотреть их через `DesignSync` как референс при реализации конкретной задачи, а сам экран собирать из `src/ui/` компонентов и настоящей модели документа.

## Архитектурные правила

**Рендерер не знает про редактор.** Функция `render(document, record) → string` в `src/render/` не обращается к DOM, не читает состояние редактора и не зависит от React. Всё, что ей нужно, приходит аргументами. Это не стилистическое предпочтение: на этой функции держатся превью, сетка миниатюр и все виды экспорта.

**Геометрия в миллиметрах.** Координаты, размеры, кегли, отступы — миллиметры в модели документа. Перевод в пиксели происходит только в компоненте холста, в одном месте. Никаких магических множителей по коду.

**Модель документа — единственный источник правды.** Редактор меняет документ, интерфейс отражает документ. Не храни позиции элементов в состоянии компонентов.

**Undo/redo с первого дня.** Любое изменение документа проходит через единый слой истории. Прикрутить это позже — переписать половину проекта.

**Данные — чистые функции в `src/data/`** (`placeholders.ts`, `problems.ts`, `csv.ts`), без DOM и React, с тестами рядом. Переполнение считается через `layoutText` (`src/render/layout.ts`) — ту же раскладку, которой пользуется `renderText`; второй копии измерений текста не заводим. Правки записей/полей как документ → документ — в `src/editor/lib/records.ts`, UI только оборачивает их в `history.set`. Текущая запись предпросмотра — состояние `EditorShell` (как зум), не документ; она же выделенная строка таблицы.

**Сохранение — в IndexedDB, не в localStorage** (`src/storage/`): картинки в документе — data URI, лимит localStorage (~5 МБ) кончается на первой фотографии. Доступ — через `idb-keyval`, свою обёртку над `IDBRequest` не пишем. `DocumentLoader` читает сессию **до** монтирования `EditorShell` — иначе автосохранение успеет записать пустой лист поверх сохранённого; пока ждём дольше 150 мс — `EditorSkeleton`. Планировщик (`storage/autosave.ts`) — чистый, с тестами; `useAutosave` только проводка. Запись коммитится явно (`transaction.commit()`) — без этого правка прямо перед F5 терялась: транзакция ждёт возврата в цикл событий, а страница уже выгружается. Всё, что меняет документ, автоматически сохраняется — отдельно звать сохранение не нужно.

**Привязки и направляющие** (`src/editor/lib/snap.ts`, `src/editor/Canvas/` — драг в `useElementDrag.ts`/`useGuideDrag.ts`) — к другим элементам, центру, обрезу/вылету/безопасному полю, и к пользовательским направляющим (тянутся с линейки, тип `Guide` в `src/model/document.ts`, живут в документе — undo/redo и сохранение работают сами по себе, не отдельный слой состояния). Резайз и перемещение примагничиваются по-разному (`snapMove` — три точки на ось у всего бокса, `snapResize` — только двигающийся край), общие приватные хелперы `axisTargets`/`bestSnap` в одном файле, не дублируются.

## Стиль кода

- TypeScript строгий, `any` не используем
- Функциональные компоненты, хуки
- Раскладка компонентов и стили `src/editor/` — по разделу «Структура `src/editor/`» ниже, для каждого нового компонента
- Комментарии объясняют **почему**, а не **что**. Комментарий вида `// увеличиваем счётчик` не нужен; комментарий `// кегль уменьшаем до 60% — ниже начинает конфликтовать с соседней колонкой` нужен
- Комментарии и сообщения коммитов на русском, идентификаторы и имена файлов на английском
- Не создавай файлы, пока они не нужны. Пустые заглушки «на будущее» не добавляй
- **Числовые поля** — `TextField` из `src/ui/forms/` уже различает числовой режим по `typeof value === "number"` (отдельный проп не нужен): стрелки вверх/вниз меняют значение на 1 (10 с Shift, 0.1 с Alt — подтягивая к ближайшей границе сетки шага, а не просто прибавляя), минус и промежуточный ввод («-», «4.») не перетираются контролируемым value на лету. Новые числовые поля — переиспользуй этот компонент, не изобретай свою обработку `onChange`/клавиш заново

## Структура `src/editor/`

Подобие FSD: слайсы с публичным API, без слоёв `app/widgets/features/entities`.

```
src/editor/
  <Component>/                 компонент верхнего уровня (Canvas, Inspector, LayersPanel, …)
    index.ts                   публичный API: сам компонент и его типы (Props и т.п.)
    <Component>.tsx
    <Component>.module.css     только если у компонента есть стили
    useSomething.ts, constants.ts   сопутствующее, нужное только этому компоненту
    <SubComponent>/            подкомпонент, нужный только родителю, — та же структура
  lib/                         логика без JSX, общая для компонентов, + *.test.ts рядом
```

Имя компонента не должно совпадать с глобалом браузера/JS — Biome (`noShadowRestrictedNames`) не пропустит: режим «Данные» поэтому `DataMode`, а не `DataView` (это типизированные массивы), по той же причине модель — `CutlineDocument`, а не `Document`.

**Новый компонент создаём так — всегда, даже если он в десять строк:**

1. Папка `<Name>/` в PascalCase, по имени компонента. Если компонент нужен только одному родителю, папка лежит внутри родителя (`Canvas/Ruler/`, `Inspector/TextInspector/`, `LayersPanel/GuideRow/`). Если нужен нескольким, она лежит рядом с ними на ближайшем общем уровне (`Inspector/PositionSizeFields/` — общий для инспекторов по типам).
2. `<Name>.tsx` — `export function <Name>` и `export interface <Name>Props`. Второй компонент в тот же файл не кладём, даже маленький: он получает свою папку (так вынесены `GuideRow` и `CanvasInspector`).
3. `index.ts` — только реэкспорт: `export { <Name> } from "./<Name>";` и `export type { <Name>Props, … } from "./<Name>";`. Логики в нём нет.
4. `<Name>.module.css` — если есть стили. Пустой не заводим, стили одного компонента в модуль другого не кладём. Правила стилей ниже.
5. Хуки и константы, нужные только этому компоненту, лежат в его папке (`Canvas/useElementDrag.ts`, `Canvas/constants.ts`). Логику без JSX, нужную нескольким компонентам или покрываемую тестами, выносим в `lib/`.

**Импорты.**
- Снаружи папки импортируем только её `index.ts`: `../Canvas`, `./Ruler`, но не `../Canvas/Canvas` и не `./Ruler/Ruler`.
- Внутри папки соседние файлы подключаем напрямую (`./constants`, `./Canvas.module.css`), а не через свой же `index.ts`, иначе будут циклы.
- `lib/` — набор независимых модулей без общего `index.ts`, импортируем конкретный файл: `../lib/snap`, `../../lib/resizeElement`.

**Стили.**
- CSS-модули. Инлайн `style` — только для значений, вычисленных из документа и зума: координаты и размеры в px, `rotate`.
- Ось или состояние задаём классом-модификатором (`.x`/`.y`, `.selected`, `.interactive`), а не условием в `style`.
- Размеры, которые уже есть в токенах, берём токеном (`var(--ruler-size)`, `var(--row-h)`), а не числом.

**`lib/`** — чистые функции (`snap.ts`, `resizeElement.ts`, `history.ts`, `createElement.ts`, `records.ts`, `plural.ts`) и хуки без JSX: `useDocumentHistory.ts` (стоит на `history.ts`), `useFontsVersion.ts`, `useAutosave.ts` (стоит на `storage/autosave.ts`). Тесты лежат рядом (`snap.test.ts`). React-компонентов тут нет.

`src/ui/` под эти правила не подпадает: это порт дизайн-системы, он остаётся плоским, на инлайн-стилях и `useHover`, как в исходнике Claude Design.

## Проверка перед тем, как считать задачу сделанной

- `npm test` проходит (Vitest)
- `npm run build` проходит без ошибок и предупреждений TypeScript
- `npm run lint` проходит без ошибок (Biome — линт и форматирование)
- Изменение проверено в браузере — по-настоящему, не только «код выглядит правильно» (см. «Как проверять в браузере» ниже)
- Экспортированный SVG открывается и совпадает с тем, что на экране
- Если трогал геометрию — проверь на карточке с очень длинным и очень коротким текстом

Новый функционал сопровождается тестами с первого коммита, не отдельным шагом потом. Тесты — `*.test.ts` рядом с модулем, `vitest` импортируется явно (без глобалов). Логику, которую хочется протестировать, выносим из хука/компонента в чистую функцию (как `lib/history.ts` из `lib/useDocumentHistory.ts`), а не тащим jsdom. То, что завязано на DOM и мышь (холст, драг, вёрстка), проверяется Playwright-сценарием по разделу ниже.

## Как проверять в браузере

Расширение Claude in Chrome есть не в каждой сессии (например, в фоновых — оно требует
живого подключённого браузера). Рабочий способ, который не зависит от этого, — headless
Playwright, гоняется через `npx`/временную установку, в зависимости проекта не входит:

```
npm run dev &                      # поднять dev-сервер
npx playwright screenshot --viewport-size=1100,1700 --wait-for-timeout=800 \
  http://localhost:5173 /путь/к/скриншоту.png
```

Если браузер ещё не скачан, `npx playwright screenshot` сам подскажет запустить
`npx playwright install chromium` (~180 МБ, один раз, дальше берётся из кеша). Файл
скриншота смотреть через Read — это реальный Chromium, не догадка по коду.

Так на этом же макете уже нашёлся реальный баг: `<svg>` из `render()` рендерился в
своём intrinsic mm-размере и вылезал под соседнюю карточку — не видно было в коде,
только на скриншоте.

**Для интерактивной проверки (клики, драг, клавиатура) одного скриншота мало** — нужен
реальный сценарий мышью/клавиатурой, а не только «код выглядит правильно». Рабочий цикл:

1. `npm install --no-save playwright` (не остаётся в `package.json`, ставится и сносится
   на время проверки)
2. Написать одноразовый скрипт `.scratch-<название>.mjs` в корне репозитория (не внутри
   `src/`, чтобы точно не попал в сборку/линт) — `chromium.launch()`, реальные
   `page.mouse.move/down/move/up`, `page.keyboard.press`, читать состояние через
   `getBoundingClientRect()`/значения полей, а не полагаться на то, что «должно было
   получиться»
3. `node .scratch-<название>.mjs`, смотреть вывод/ассерты
4. Убрать `.scratch-*.mjs`, `npm uninstall --no-save playwright`, поднять dev-сервер
   заново для следующей сессии, если нужно

Этим способом в этой же сессии ловились реальные баги, которые не видны по коду: клик
без движения мыши по направляющей неотличим от «отпустили над линейкой» и удалял её;
эффект с `mousemove`/`mouseup` подписывался на устаревшее значение из замыкания вместо
свежего аргумента апдейтера; перепутанная ось при перетаскивании с линейки.

**Для рефакторинга без изменения поведения** — снять эталон до правок и сравнивать попиксельно
после каждого шага: тот же скрипт сохраняет скриншоты ключевых состояний (пусто, выделение,
середина драга со снапом, направляющая, переполнение текста, бейдж) + итоговые значения полей
инспектора + экспортированный SVG, а одноразовый `.scratch-diff.mjs` сравнивает папки через
`pixelmatch`/`pngjs` (`npm install --no-save`). Прогон дважды на одном коде должен дать 0
отличий — иначе сценарий недетерминирован и сравнение ничего не доказывает.

**IndexedDB в сценариях.** Состояние теперь переживает `page.reload()` и живёт в профиле контекста — для чистого старта бери новый `browser.newContext()`. Медленный или сломанный IndexedDB подменяется через `context.addInitScript` на `IDBFactory.prototype.open` (задержка — чтобы увидеть скелетон; `throw` — режим «хранилище недоступно»). Перед `reload` после правки жди конца дебаунса («Сохранено» висит и до правки — сначала `waitForTimeout(700)`), иначе сработает вопрос `beforeunload`.

**Подводные камни локаторов.** Под редактором на странице ещё витрина UI-кита (`UiKitDemo` в `App.tsx`) — там свои `RecordNavigator`, `FieldToken` и т.п., поэтому `getByText`/`getByRole` часто находят два элемента: бери `.first()`. Та же витрина содержит свой переключатель «Дизайн | Данные» — ожидание `getByRole("radio", { name: "Дизайн" })` не доказывает, что редактор загрузился. Переключатель «Дизайн | Данные» — `role="radio"`, не `button`. SVG карточки на холсте — `svg[viewBox="0 0 105 148"]`, а не первый `svg` на странице (это иконка). `outerHTML` SVG из DOM не равен строке `render()` побайтно (`<rect …></rect>` вместо `<rect …/>`) — сравнивай содержимое, а не байты.

**Субпиксельный шум измерений.** `getBoundingClientRect()`/`boundingBox()` в этом
окружении дают шум порядка 0.1–0.3мм (иногда до ~1px) — сама карточка холста
перецентровывается при росте контента, поэтому кэшировать её координаты один раз в
начале скрипта нельзя, брать свежими перед каждым действием. Если ассерт с точным
номинальным значением падает на пару десятых мм — это почти наверняка шум измерения,
а не баг: сравнивай с реально измеренным состоянием (прочитать текущую позицию элемента/
направляющей из DOM), а не с тем, что «должно было получиться» по арифметике, и давай
допуск ~0.2–0.3мм на такие сравнения.

## Коммиты

Крупную фичу делим на несколько осмысленных коммитов, а не на один большой diff — каждый коммит должен быть самодостаточным шагом, а не случайной точкой остановки.

После того как работа закончена и проверка выше пройдена — коммить. Но не `git push`: пуш только по отдельной явной просьбе.

## Чего не делаем в первой версии

Группы и слои-папки, кривые Безье, тени и эффекты, совместное редактирование, аккаунты, облачное хранение, версионирование документов, мобильное редактирование.

Каждый пункт выглядит как небольшая добавка и каждый стоит недели. Если возникает соблазн — предложи, но не начинай без подтверждения.

## Известные подводные камни

**Текст — самая трудоёмкая часть.** Переносы, автоподгонка по кеглю, выравнивание по базовой линии съедают больше времени, чем весь остальной редактор. Закладывай это в оценки.

**Измерение текста.** В прототипе ширина строки считается через canvas `measureText` для системных шрифтов и через метрики opentype.js для загруженных. Превью и экспорт обязаны использовать один и тот же способ измерения, иначе вёрстка разъедется между экраном и печатью.

**Загрузка веб-шрифтов.** Canvas `measureText` меряет тем шрифтом, что загружен сейчас: пока шрифт документа догружается, текст меряется запасным (он уже), и длинное имя «влезает». Всё, что мемоизировано по документу и зависит от измерения (проблемы, миниатюры), берёт в зависимости `useFontsVersion()` — иначе первая подсветка проблем остаётся посчитанной по запасному шрифту. Реальный баг Этапа 3: холст рисовал запись обрезанной, а сетка её не обводила.

**Файлы .ttc не парсятся** opentype.js. Menlo и Monaco на macOS лежат именно в коллекциях — нужна понятная ошибка с объяснением, а не молчаливый сбой.

**Печать без полей.** Четыре карточки A6 закрывают A4 целиком, места под поля не остаётся. Домашние принтеры срезают 3–5 мм с каждого края. Спуск полос должен это учитывать и предлагать вариант с уменьшением.
